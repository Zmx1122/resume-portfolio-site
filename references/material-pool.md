# 资料池：收集、提取、交叉比对

资料池是这个技能和"套模板做网站"的根本区别。用户手里往往有一整套 Bewerbungsmappe：好几个版本的简历、给不同公司写的求职信、前雇主出具的 Arbeitszeugnis、证书、成绩单……每份材料只讲了TA的一部分，而且彼此之间常有出入。你的任务是把它们拼成一张完整、可信的图，再从图上的空白和矛盾出发去采访。

## 目录

1. 收集与分类
2. 资料卡

## 1. 收集与分类

**接受任何格式**：PDF、扫描件或手机拍照、Word、截图、直接粘贴的文字。不要求用户改文件名或整理顺序。看不清的扫描件，告诉用户哪一页看不清，请TA重拍或直接口述关键信息。

**每份材料编号** M01、M02……按收到的顺序编，之后用户补的材料继续往后编。同一份材料的多页算一个编号。

**判断类型**。先看标题和抬头，再看内容。常见识别线索：

| 类型 | 识别线索（德 / 英 / 中） | 提取规则 |
|---|---|---|
| 简历 | Lebenslauf, Curriculum Vitae, CV, Resume, Europass, 简历；LinkedIn 导出的 PDF 也算这一类 | `doc-types/cv.md` |
| 求职信 | Anschreiben, Bewerbung als …, Motivationsschreiben, Cover Letter, Statement of Purpose, 求职信, 个人陈述 | `doc-types/cover-letter.md` |
| 工作证明 | Arbeitszeugnis, Zwischenzeugnis, Praktikumszeugnis, Arbeitsbescheinigung, Praktikumsbescheinigung, Employment Certificate, 实习证明, 工作证明, 离职证明 | `doc-types/arbeitszeugnis.md` |
| 推荐信 | Empfehlungsschreiben, Referenzschreiben, Letter of Recommendation, Reference Letter, 推荐信 | `doc-types/recommendation.md` |
| 证书 | Zertifikat, Certificate, Teilnahmebescheinigung, Goethe-Zertifikat, TestDaF, telc, DSH, IELTS, TOEFL, 语言证书, 职业资格证, 课程结业证 | `doc-types/certificate.md` |
| 成绩与学位 | Notenspiegel, Transcript of Records, Leistungsübersicht, Bachelorzeugnis, Masterzeugnis, Urkunde (Hochschulgrad), Abiturzeugnis, 成绩单, 学位证, 毕业证 | `doc-types/transcript.md` |
| 在读证明 | Immatrikulationsbescheinigung, Studienbescheinigung, Enrollment Certificate, 在读证明, 学籍证明 | `doc-types/enrollment.md` |
| 获奖与奖学金 | Urkunde (Wettbewerb), Preis, Auszeichnung, Stipendium, Deutschlandstipendium, DAAD, Award, Scholarship, 获奖证书, 奖学金证明 | `doc-types/award.md` |
| 其他 | 作品截图、项目照片、论文、海报、演示文稿、GitHub 链接、个人照片 | 本文件"其他材料" |

**容易混的两种 Zeugnis**：德语里 Zeugnis 既可以指雇主出具的工作证明（Arbeitszeugnis），也可以指学校的成绩或学位证明（Bachelorzeugnis、Abiturzeugnis）。看出具方：公司 → 工作证明；学校 → 成绩与学位。

**一份材料可能同时属于两类**。例如一封带成绩评价的实习证明，或者一张同时写了获奖和奖学金的证书。按主要用途归类，在资料卡里注明"也包含 …"。

### 其他材料

- **作品截图、项目照片**：问清楚是哪段经历、图里是什么、能不能公开（公司内部系统的截图常有保密问题）。它们是故事页最好的配图。
- **论文、海报、演示文稿**：提取题目、发表处或场合、日期、合作者、一句话结论。论文可以成为一个独立故事。
- **个人照片**：确认用户是否愿意在网站上放头像。德国求职简历常带照片，但网站上放不放由用户决定。
- **链接**（GitHub、个人博客、作品集平台）：能打开就读公开内容；打不开就请用户描述或截图。

## 2. 资料卡

每份材料提取完，在 `_work/pool.md` 里写一张资料卡。格式：

```markdown
### M03 · Arbeitszeugnis · Muster GmbH
- 类型：工作证明（qualifiziertes Arbeitszeugnis，带评价）
- 日期：2025-09-30
- 语言：德语
- 对应经历：Werkstudent Data Analytics，Muster GmbH，2024-04 至 2025-09
- 提取要点：
  - 职责：搭建销售数据看板（Power BI）；每月自动化报表；支持 3 个部门的数据需求
  - 评价：工作表现 ≈ 很好（"stets zu unserer vollsten Zufriedenheit"）；行为评价 ≈ 很好
  - 被点名的优点：独立工作、分析能力强、和同事合作好
  - 可引用：„… überzeugte durch seine strukturierte und eigenständige Arbeitsweise."
- 敏感信息：出生日期、住址、签名 → 不公开
- 建议用途：Muster GmbH 故事页的证据摘录；技能"Power BI"的证据
- 发现：看板项目两版简历都没写 → 已加入待问问题 Q07
- 默认公开级别：只展示摘要
```

资料卡要短。它的作用是让你（和用户）随时能回顾"每份材料说了什么"，而不是把原文抄一遍。

## 3. 敏感度分级

每份材料、以及材料里的每类信息，都有一个公开级别。你给默认建议，用户随时可以改。开场时已经说明过：上传给 AI 的信息由用户自己负责，所以这里的分级是为了**网站上公开什么**，不是为了拒绝处理。

| 级别 | 含义 | 网站上怎么显示 |
|---|---|---|
| 公开 | 可以原样展示 | 文件放进 `site/assets/`，可以在线查看 |
| 只展示摘要 | 内容可以用，原件不放 | 只展示你写的摘要或短引用，标明出处（例如"摘自 Muster GmbH 工作证明"） |
| 可按需提供 | 告诉 HR 有这份文件 | 文件墙里显示一张卡片，写"可按需提供 / Auf Anfrage / Available on request" |
| 不公开 | 只用于你内部分析 | 网站上完全不出现 |

**各类材料的默认级别**：

| 材料 | 默认 |
|---|---|
| 简历、求职信 | 不公开原件；内容拆进网站各版块 |
| 工作证明、推荐信 | 只展示摘要（推荐信的引用需要推荐人同意，见对应规则） |
| 语言证书、职业证书 | 公开（遮住证书编号以外的个人信息），或只放验证链接 |
| 成绩单 | 可按需提供；相关课程和毕业论文可以写进网站 |
| 学位证、毕业证 | 可按需提供 |
| 在读证明 | 不公开；只用来推导可工作时间 |
| 获奖证书 | 公开或只展示摘要 |
| 作品截图、项目照片 | 公开（确认无保密问题后） |

**以下信息无论用户怎么选，都先提醒一次再公开**：出生日期和出生地、完整住址、证件号码（护照、身份证、Steuer-ID、社保号）、学号或 Matrikelnummer、签证或居留信息、APS 证书编号、手写签名、照片里的其他人。用户确认要公开，就按TA的意思办。

## 4. 事实台账

`_work/facts.md` 记录每一条会写进网站的事实。它保证"网站上每句话都有来源"，也是交叉比对的基础。

```markdown
| ID | 事实 | 来源 | 可信度 | 状态 |
| --- | --- | --- | --- | --- |
| F012 | 2024-04 起在 Muster GmbH 任 Werkstudent Data Analytics | M01, M02, M03 | 材料写明 | 已确认 |
| F013 | 入职时间 2024-03 还是 2024-04 | M01 写 03/2024，M03 写 01.04.2024 | 冲突 | 待问 Q05 |
| F021 | 销售看板每月节省约 10 小时人工 | I08 | 用户口述 | 已确认 |
```

- **来源**：M 开头是材料，I 开头是采访回答（在 `_work/interview.md` 里编号）。
- **可信度**：材料写明 > 用户口述 > 你的推断。推断出来的内容（比如"TA应该会 SQL"）不能直接上网站，要先问用户。
- **状态**：已确认 / 待问 / 冲突 / 已跳过。只有"已确认"的事实能进入 `content.js`。

## 5. 交叉比对

所有材料都提取完（或者用户说"就这些"）之后，做一遍交叉比对。比对的产出是**待问问题**和**内容建议**，不是直接改结论。

### 5.1 合并同一个实体

同一家公司、学校、项目，在不同材料里写法常不一样："Muster GmbH" / "Muster" / "穆斯特公司"；"TUM" / "Technische Universität München"。把它们合并成一个实体，后面统一用正式名称，资料卡里记下别名。

### 5.2 找冲突

| 冲突类型 | 例子 | 处理 |
|---|---|---|
| 时间 | 简历 A 写 03/2024 入职，工作证明写 01.04.2024 | 以官方文件为准提出建议，问用户确认 |
| 职位名称 | 简历写 "Data Analyst"，工作证明写 "Werkstudent im Bereich Controlling" | 网站以正式职位为准，可以在描述里说明实际工作内容；问用户 |
| 成绩 | 简历写 GPA 3.6，成绩单换算后不一致 | 问用户以哪个为准，以及要不要展示成绩 |
| 语言水平 | 简历写德语 C1，证书是 B2 | 网站以证书为准，或写"B2 证书，目前工作语言为德语"；问用户 |

**冲突要问，但问法要中性。** 用户的旧简历写得不准很常见，不要让TA觉得被抓到了错误。例如："两份材料里入职时间差一个月，网站上用哪个？"

### 5.3 找隐藏亮点

这是资料池最有价值的地方。**在某份材料里出现、但简历里没有或只轻描淡写的内容**，往往就是最好的故事素材：

- 工作证明的职责清单里有，简历没写的项目
- 推荐信里提到的具体事例
- 求职信里讲过、简历里没有的经历或动机
- 成绩单里和目标岗位高度相关、成绩又好的课程
- 获奖证书背后的项目
- 照片和截图里能看出来、但用户从没提过的东西

### 5.4 找缺证据的说法

简历和求职信里的自我评价（"沟通能力强""精通 Python""有领导力"），在其他材料里有没有支撑？有就挂上证据；没有就问用户要一个具体例子。没有例子的形容词，网站上宁可不写。

### 5.5 看定位差异

用户给不同公司投的简历版本，强调的东西往往不同，这能看出TA在几个方向之间犹豫。把这些方向列出来，在采访模块 A 里请TA选一个主方向。网站只能有一个清晰的定位；次要方向可以作为补充版块。

### 5.6 时间线空档

超过 3 个月的空档可以问一次，但标为【可选】，语气中性，例如："2023 年 7 月到 10 月这段时间，有什么想放在网站上的吗？比如语言学习、旅行、个人项目。也可以不写。"用户不想说就跳过。

## 6. 生成采访问题

比对的每个发现都转成一个问题，写进 `_work/questions.md`：

```markdown
| ID | 问题 | 来自 | 模块 | 标签 | 状态 |
| --- | --- | --- | --- | --- | --- |
| Q05 | 两份材料里入职时间差一个月（03/2024 和 04/2024），网站上用哪个？ | F013 | C | 必填 | 待问 |
| Q07 | 工作证明里提到你搭过销售数据看板，简历里没写。能讲讲它解决了什么问题、有多少人在用吗？有截图更好。 | M03 | C | 推荐 | 待问 |
| Q11 | 2023-07 到 2023-10 有什么想放在网站上的吗？ | 时间线 | C | 可选 | 待问 |
```

**排序规则**：先【必填】，再按"对网站质量的影响"排【推荐】（能成为精选故事的线索排最前），最后【可选】。每轮从当前模块里取最多 3 个。

**问题要能直接回答。** 一个问题只问一件事；给出你已经知道的信息，让用户只补缺的部分；需要文件时明说"有截图或照片可以直接拖进来"。

## 7. 资料池报告（给用户看的）

交叉比对完成后，发给用户一份简短报告，然后进入采访：

```markdown
我看完了你的 7 份材料：

| 编号 | 材料 |
| --- | --- |
| M01、M02 | 简历（2025 年 3 月版、2025 年 9 月版） |
| M03 | Muster GmbH 工作证明 |
| M04 | 求职信（投给 Beispiel AG） |
| M05 | TestDaF 证书 |
| M06 | 硕士成绩单 |
| M07 | 在读证明 |

我发现了：
- **3 个可以重点展示的亮点**，比如工作证明里提到的销售数据看板，简历里还没写
- **2 处需要你确认的地方**，比如入职时间两份材料差一个月
- **1 个可以补充的空白**：还没有项目的照片或截图

接下来我会问你一些问题，每次最多 3 个。不想回答的直接说"跳过"就行。
```

报告里不要列出所有细节，挑最能让用户觉得"它真的读懂了我的材料"的两三个例子。
