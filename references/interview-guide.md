# 采访指南

SKILL.md 里已经写了采访的顺序和基本规则。这份文件补充三样东西：每个模块的问题库、把一句话挖成故事的追问技巧、以及用户卡住或不配合时怎么办。

问题库里的问题是**素材，不是剧本**。优先问 `_work/questions.md` 里由资料池生成的问题；问题库只用来补资料池覆盖不到的地方。用户已经在材料里回答过的，不要再问。

## 目录

1. 提问的基本功

3. 把一句话挖成故事
4. 收集图片和文件
5. 改写与确认
6. 特殊情况

## 1. 提问的基本功

- **先给已知，再问未知。** "我看到你 2024 年 4 月开始在 Muster GmbH 做 Werkstudent，主要做数据报表。这段经历里，你觉得最拿得出手的一件事是什么？"用户只需要补充，不需要从头讲。
- **一个问题只问一件事。** "你做了什么、结果如何、有没有截图？"是三个问题，拆开问，或者明确写成 1、2、3。
- **给回答的样子。** 不知道怎么答的用户，看到一个例子就会答了："比如'每月省了 10 小时手工整理'或者'报表从两天缩短到半小时'这样。"
- **接受模糊的数字。** "大概多少？给个范围也行。"范围比没有强得多。记录时注明是估计值。
- **每轮结尾给出路**："不想回答的说'跳过'，不确定的说'你帮我建议'。"前几轮每次都提醒，之后用户熟悉了可以省略。
- **每个模块结束时小结一次**："关于求职目标，我记下了：…… 有要改的吗？"这能及时纠正误解，也让用户有进度感。

## 2. 问题库

【必填】的问题，用户跳过时要说明后果（例如"不确定岗位方向的话，首页的介绍会写得比较宽泛"），但不再追问。

### A 求职目标

| 标签 | 问题 |
|---|---|
| 必填 | 你现在主要在找什么类型的工作？Werkstudent、实习、毕业论文、全职，还是读博？ |
| 必填 | 想做什么方向的岗位？说一两个职位名称就行，比如"数据分析""产品经理""嵌入式开发"。 |
| 必填 | 你想要网站用哪些语言？最多三种，第一种是默认语言。（建议见 SKILL.md） |
| 推荐 | 想在哪些城市找？还是哪里都可以？ |
| 推荐 | 最早什么时候可以开始？每周能工作多少小时？ |
| 可选 | 有特别想去的公司或行业吗？（只用来调整措辞，不会写上网站） |

资料池显示用户在几个方向之间犹豫时（见 `material-pool.md` 5.5），把方向列出来让用户选："你投过数据分析和产品两类岗位。网站最好有一个主方向，你想以哪个为主？另一个可以作为补充。"

### B 基本信息

| 标签 | 问题 |
|---|---|
| 必填 | 网站上你的名字想怎么写？比如 "Xiao Lin"、"Lin Xiao"，或者加上中文名。 |
| 推荐 | 用一句话介绍自己，你会怎么说？（说不出来就说"你帮我建议"，我根据材料写几个版本给你挑） |
| 推荐 | 哪些联系方式可以放在网站上？邮箱、LinkedIn、GitHub、电话？ |
| 推荐 | 网站上放头像吗？ |
| 推荐 | 你的语言水平：每门语言平时用来做什么？（有证书的我已经从材料里读到了） |

### C 经历深挖

对每段重点经历（通常 2–4 段，优先挑资料池标出的亮点），用第 3 节的方法挖。开场可以这样问：

> 在 Muster GmbH 的这段经历里，如果只能讲一件事给面试官听，你会讲哪件？

### D 项目与作品

| 标签 | 问题 |
|---|---|
| 推荐 | 毕业论文（或正在写的论文）是关于什么的？解决了什么问题？ |
| 推荐 | 有没有课程项目、个人项目、比赛，是你特别满意的？ |
| 可选 | 有没有能公开的作品：代码仓库、报告、海报、演示视频、设计稿？ |

### E 个人故事

| 标签 | 问题 |
|---|---|
| 可选 | 为什么选了这个专业或方向？ |
| 可选 | 为什么来德国？ |
| 可选 | 工作之外喜欢做什么？ |

这一模块全部是可选的。用户给的回答很短也没关系，"关于我"版块两三句话就够了。

### F 网站偏好

| 标签 | 问题 |
|---|---|
| 推荐 | 你希望别人看到网站时的第一感觉是什么？比如"专业可靠""有创意""技术很强""亲切"。 |
| 可选 | 有没有你喜欢的个人网站，或者喜欢的网站风格？发链接或截图都行。 |
| 可选 | 有没有哪个版块你不想要？比如不想放成绩、不想放兴趣爱好。 |

风格的最终选择在阶段 6 用小样完成，这里只收集方向。

## 3. 把一句话挖成故事

一个好的故事有四个部分：**背景或问题 → 用户亲手做了什么 → 结果 → 证据**。简历上通常只有一句"负责 X"，需要按顺序追问。

| 要补的部分 | 追问 |
|---|---|
| 背景 | 当时遇到了什么问题？如果没人做这件事，会怎样？ |
| 行动 | 这件事里，哪部分是你亲手做的？用了什么方法或工具？有没有遇到什么难点，你是怎么解决的？ |
| 结果 | 做完之后有什么变化？有多少人在用？省了多少时间或钱？有没有人给过反馈？ |
| 证据 | 有截图、照片、报告或者别人的评价吗？工作证明或推荐信里有没有提到？ |

### 找数字的办法

用户常说"没有数字"。其实大部分经历都能找到可以量化的东西，换个角度问：

- **规模**：多少用户、多少数据、多少个部门、多少个国家、多大的预算
- **频率**：每天、每周、每月用几次
- **时间**：以前要多久，现在要多久
- **数量**：做了几个、处理了多少、带了几个人
- **对比**：比之前快了多少、错误少了多少
- **认可**：被采用、被推广到别的团队、被写进流程、拿了奖

用户只能给估计值时，记下"约"并在 `facts.md` 里标为"用户口述"。**不要替用户编一个看起来合理的数字。**

### 分清"我"和"我们"

团队项目里，用户常说"我们做了……"。追问一次"这里面你负责的是哪部分"，网站上写用户自己的贡献，团队的成果作为背景。不需要夸大，HR 很看重诚实的分工描述。

## 4. 收集图片和文件

图文并茂的故事页需要配图。问的时候具体说要什么：

- **截图**：系统界面、看板、代码运行结果。提醒用户先把真实数据、客户名、同事姓名遮住，或者截图前换成演示数据。
- **照片**：活动现场、海报展示、产品实物、团队合影（合影里有其他人，问用户是否征得同意）。
- **图表**：论文或报告里的关键图。
- **文件**：报告、海报、演示文稿。能公开的可以放在故事页供下载。

每张图都问一句"这张图里是什么"，作为图片说明的素材。用户说"这是我们的看板"，你写成"销售看板总览页，数据已脱敏"。

公司内部的东西，问一次"这个能公开吗？有没有保密要求？"用户不确定时，建议不放，或者只用文字描述。

## 5. 改写与确认

把用户的口语改写成网站文字后，**一定给用户看并确认**。展示时给出前后对比：

> 你说的：就是帮老板做了个表，后来大家都在用
>
> 我改写成：用 Power BI 搭建销售看板，现在销售、财务和采购三个部门都在用
>
> 这样写准确吗？有要改的地方吗？

改写原则：

- **动词开头，写具体动作。** 搭建、设计、分析、自动化、组织、谈判。少用"负责""参与""协助"。
- **结果放在能看到的地方。** 有数字的放数字。
- **不加形容词。** "成功地""高效地""出色地"都删掉，让事实说话。
- **保留用户的声音。** 措辞要像用户自己能说出口的话，面试时 HR 会问到，用户要能讲得出来。
- 德语和英语的写法，见 `content-model.md` 的翻译规则。

## 6. 特殊情况

| 情况 | 怎么办 |
|---|---|
| 用户回答很短，比如"嗯""还行""没什么" | 换成选择题："这段经历更接近 A 做数据报表，还是 B 做数据分析给建议？" |
| 用户说"我没什么可写的" | 回到资料池找证据："你的工作证明里提到了 X 和 Y，这些都值得写。"大多数人低估自己。 |
| 用户一次说了很多 | 先总结要点给用户确认，再从中挑出最适合做成故事的部分 |
| 用户想快点结束 | 只问剩下的【必填】问题，其余记为"以后补"，直接进入缺口报告 |
| 用户中途离开，下次回来 | 读 `_work/` 里的文件，先用两三句话说明进度："上次我们聊完了求职目标和第一段经历，还剩……" |
| 涉及敏感话题：空档期、挂科、换专业、签证、健康 | 只问一次，标为【可选】，语气中性。用户不想说就跳过，网站上不写。不要追问原因。 |
| 用户想写没有依据的内容，比如"精通 10 种编程语言" | 不直接拒绝，问一个具体例子；没有例子，建议换成能证明的说法，例如"在项目里用过 Python、SQL 和 R" |
| 用户提供的信息和材料矛盾 | 按 `material-pool.md` 5.2 中性地确认，以用户最终确认的为准 |
| 用户问"别人一般怎么写" | 给 2–3 个不同风格的写法让用户挑，不要只给一个 |
