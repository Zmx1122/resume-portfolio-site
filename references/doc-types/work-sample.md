# 作品和项目材料（项目报告、展示幻灯片、代码仓库、海报、演示视频、截图）

作品材料把"我做过一个项目"变成"你可以亲眼看到我做了什么"。它们是故事页最好的配图和链接，要**主动去要**（见 `best-practice-checklist.md` 的 C 节）。

## 识别

| 材料 | 识别线索 |
|---|---|
| 项目报告 | 课程项目报告、Projektbericht、技术文档、实验报告 |
| 展示幻灯片 | PPT、Keynote、PDF 格式的展示稿；常有一页总结架构或结果 |
| 代码仓库 | GitHub、GitLab 链接；README 里有项目说明 |
| 海报 | 会议或课程海报，一页 A0/A1 |
| 演示视频 | 屏幕录像、产品演示 |
| 截图和照片 | 系统界面、看板、硬件、现场照片 |

## 提取

| 字段 | 说明 |
|---|---|
| 属于哪段经历 | 课程、实习、比赛、个人项目；对应到已有的经历或故事。属于已有经历的，**不要新建一段经历** |
| 时间 | 至少到年月 |
| 团队和用户的角色 | 几个人、用户亲手做的部分 |
| 问题、做法、结果 | 报告和幻灯片的结构通常就是这三段；优先找带数字的结果 |
| 技术和工具 | 写进故事的技能标签 |
| 一张代表性的图 | 架构图、结果图、界面截图，作为故事页配图 |
| 链接 | 代码仓库、演示视频、在线 Demo |

### 代码仓库

- 只读公开内容：README、使用的语言和框架、最近的提交时间。不要要求用户提供访问私有仓库的权限或令牌。
- README 写得好、能直接看懂的仓库，在故事页放链接；没有 README 或内容很乱的，建议用户先补一个简单的 README，或者不放链接。
- 很久没更新的仓库也可以放，在故事里写清楚是哪一年的项目。

### 幻灯片和报告

- 优先用里面现成的架构图、流程图、结果图，截图作为配图。
- 幻灯片上的标题不一定是论文或项目的正式名称；正式名称从报告封面、论文或用户那里确认。

### 截图和照片

- 裁掉手机界面、浏览器边框等无关部分。
- 遮住或换掉真实客户名、同事姓名、内部数据；不确定能否公开的，问用户。
- 照片里有其他人的，问用户是否征得同意。
- 每张图写一句说明文字（`caption`）和替代文字（`alt`），每种语言都要有。

## 网站用途

- 故事页的配图（`media`，`type: "image"`）和链接（`type: "link"`）
- 证据：可以公开的报告或海报，作为文件放进文件墙（`documents`）
- 技能标签

## 公开前的检查

- 公司内部的材料（报告、截图、代码）默认**不公开**，先问用户有没有保密要求
- 课程项目和个人项目一般可以公开，但团队项目里别人写的部分，不要说成用户自己做的
- 要公开的 PDF 放进网站文件夹前，确认里面没有电话、住址等个人信息（检查脚本会读 PDF 文字）
