# 简历（Lebenslauf / CV / Resume / LinkedIn 导出 PDF）

简历是资料池的骨架：它给出经历的清单和时间线，其他材料往上面补血肉。用户常会给好几个版本，**版本之间的差异本身就是信息**。

## 识别

- 德式表格简历（tabellarischer Lebenslauf）：通常有照片、个人信息栏、倒序时间线，日期写成 `MM/YYYY` 或 `seit MM/YYYY`
- Europass：蓝色抬头，固定栏目，语言能力用欧标表格
- 英文 Resume：常无照片，一页，项目符号多
- 中文简历：可能写"求职意向""自我评价"，日期写成 `2023.09–2024.06`
- LinkedIn 导出 PDF：左栏有 Contact / Top Skills / Languages，右栏是 Summary 和 Experience；非英文字符有时显示不正常，遇到乱码就请用户确认原文

## 提取

**版本信息**（每个版本一条）：版本日期（文件日期或内容推断）、语言、投递目标（文件名、求职信或用户说明里能看出来的话）、篇幅。

**每段经历**：

| 字段 | 说明 |
|---|---|
| 机构 | 正式名称；记下别名 |
| 职位 | 原文照录，不要自己翻译成别的头衔 |
| 类型 | Vollzeit / Werkstudent / Praktikum / HiWi（学校科研助理）/ Abschlussarbeit / Ehrenamt / Freelance / 兼职 |
| 地点 | 城市；远程注明 |
| 起止时间 | 统一成 `YYYY-MM`；"至今"留空结束时间 |
| 要点 | 每条原文保留，后面再改写 |
| 提到的技能和工具 | 逐条列出，后面汇总进技能表 |

**其他版块**：教育（学校、专业、学位、时间、成绩、论文题目）、语言（自评等级和证书）、技能、证书、获奖、志愿活动、兴趣爱好、自我评价或 Profil 一段话。

## 多版本处理

1. 按机构和时间把各版本的同一段经历对齐，合并成一条，记下每个版本的写法。
2. 取**信息最全**的那条作为底稿，但每个细节都要能在某个版本里找到。
3. 比较各版本突出了什么：投数据岗的版本突出 SQL 和看板，投产品岗的版本突出需求和沟通。把这些方向写进资料卡的"定位"一栏，交给交叉比对的 5.5。
4. 某个版本里出现、其他版本删掉的经历，问一句为什么删（可能是不相关，也可能是不想公开）。

## 深挖线索

- **只有动作没有结果的要点**："负责数据分析""unterstützt bei …""responsible for …"。追问：做了什么具体的事？结果是什么？有没有数字？
- **弱动词**：负责、参与、协助 / zuständig für、mitgewirkt、unterstützt / helped、assisted、was involved in。它们往往掩盖了用户真正做过的事，追问"你自己亲手做的是哪部分"。
- **某段经历在一个版本里写得特别详细**：用户自己觉得这段重要，优先挖成故事。
- **技能栏有、经历里没出现的技能**：问在哪里用过，没有用过的场景就不在网站上强调。
- **自我评价里的形容词**：交给交叉比对 5.4 找证据。

## 网站用途

- 经历和教育 → 时间线和各经历条目
- 写得最详细、和目标岗位最相关的 2–4 段 → 精选故事候选
- 技能 → 技能索引（每项技能要挂到至少一个故事上）
- Profil / 自我评价 → 首页定位语的素材（要重写，不要照搬）

## 敏感信息

德式简历常带出生日期、出生地、国籍、婚姻状况、完整住址、照片。按 `material-pool.md` 的规则处理：默认不进网站，照片要问用户。

## 常见坑

- 日期格式混乱（`03/24`、`2024.3`、`März 2024`），统一前先确认年份没有歧义。
- 同一时间段有多段经历重叠（比如读书同时做 Werkstudent），这是正常的，不是冲突。
- 用户给的英文简历里职位是自己翻译的，和工作证明上的德语原职位不一致，以正式职位为准，问用户。
